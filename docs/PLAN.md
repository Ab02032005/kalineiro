# Kali — структура, план, модели, тесты, риски (Этап 1, часть 2)

## 6. Структура каталогов

```
Kali/
├── docs/                    # архитектура, решения (ADR), руководства
│   ├── ARCHITECTURE.md
│   ├── PLAN.md
│   └── adr/                 # записи о принятых решениях
├── backend/
│   ├── kali/
│   │   ├── core/            # оркестратор, конвейер запроса, состояние
│   │   ├── api/             # FastAPI-роуты, схемы, SSE
│   │   ├── auth/            # пользователи, токены, роли, права
│   │   ├── models/          # Model Gateway: адаптеры провайдеров
│   │   │   ├── base.py      # интерфейс LLMProvider
│   │   │   ├── providers/   # openai_compatible.py, groq.py, ollama.py ...
│   │   │   └── registry.py

│   │   ├── knowledge/       # загрузка, чанкование, индекс, RAG
│   │   ├── tools/           # Tool Engine, реестр, базовые инструменты
│   │   │   ├── base.py
│   │   │   ├── calculator.py
│   │   │   ├── files.py
│   │   │   ├── web_search.py
│   │   │   ├── images.py
│   │   │   └── python_exec.py
│   │   ├── agents/          # специализированные агенты (этап 2+)
│   │   ├── planning/        # машина состояний задач
│   │   ├── verification/    # проверка ответов и фактов
│   │   ├── multimodal/      # документы, изображения, речь (адаптеры)
│   │   ├── security/        # фильтры входа/выхода, защита от injection
│   │   ├── sandbox/         # изоляция выполнения кода
│   │   ├── learning/        # обратная связь, датасеты, оценка
│   │   ├── audit/           # журнал действий
│   │   └── config/          # настройки через переменные окружения
│   ├── tests/
│   │   ├── unit/
│   │   ├── integration/
│   │   └── eval/            # наборы для оценки качества
│   ├── pyproject.toml
│   └── Dockerfile
├── frontend/                # Next.js + TypeScript (этап 3+); MVP — static/
├── infra/
│   ├── docker-compose.yml   # backend, postgres, redis, qdrant, ollama
│   ├── sandbox/             # образ для выполнения кода
│   └── monitoring/          # Prometheus/Grafana (этап 2)
├── data/                    # локальные данные (в .gitignore)
│   ├── uploads/
│   ├── generated/
│   └── datasets/

├── .github/workflows/       # CI
├── .env.example
```

Правила: каждый модуль в `kali/` имеет `__init__.py` с публичным интерфейсом, внутренние детали скрыты. Модули общаются через интерфейсы из `base.py`, а не напрямую.

## 7. План реализации по этапам

Каждый этап заканчивается проверяемым результатом.

**Этап 2. Основа проекта.** Создать структуру, `pyproject.toml`, конфигурацию через переменные окружения, логирование в JSON, базовый FastAPI-сервер с `/health`, Docker Compose для локального запуска. *Готово, когда:* `docker compose up` поднимает сервис, проходит тест `/health`.

**Этап 3. Ядро и Model Gateway.** Интерфейс `LLMProvider`, адаптер OpenAI-совместимого API (покрывает ChatAnywhere, Groq, OpenRouter, Ollama), реестр провайдеров, Core-конвейер без памяти и инструментов. Потоковые ответы через SSE. *Готово, когда:* один и тот же запрос проходит через два разных провайдера, переключение — настройкой.

**Этап 4. Память.** Краткосрочная (окно диалога с суммаризацией), долговременная и семантическая (факты с источником и временем), эпизодическая (история взаимодействий), процедурная (сохранённые шаблоны решений). Поиск по эмбеддингам, обновление и удаление по запросу, экспорт в JSON. *Готово, когда:* факт, сказанный в одном диалоге, найден в другом, а после удаления — не находится.

**Этап 5. Знания (RAG).** Загрузка TXT, MD, PDF, DOCX, CSV, XLSX, чанкование с сохранением структуры, эмбеддинги (bge-m3 или multilingual-e5-small), гибридный поиск, ответы со ссылками на фрагменты. *Готово, когда:* ответ по загруженному документу содержит ссылку на нужный фрагмент, а вопрос вне документа честно помечается как «не найдено в базе».

**Этап 6. Инструменты и агенты.** Tool Engine с JSON-схемами, правами и подтверждением опасных действий. Инструменты: калькулятор, файлы, интернет-поиск, генерация изображений, Python в sandbox. Базовые агенты (Research, Coding, Math, QA), которые используют инструменты и передают результаты друг другу. *Готово, когда:* добавление нового инструмента требует только нового файла в `tools/`, без правок ядра; код в sandbox не имеет доступа к сети и файлам хоста.

**Этап 7. Пользовательский интерфейс.** Chat, Projects, Memory, Agents, Knowledge, Files, Models, Settings, Dashboard, Admin. Тёмная и светлая темы, адаптивность. Каждый раздел подключён к реальной логике, без заглушек. *Готово, когда:* каждый раздел выполняет свою функцию на реальных данных, проверено на телефоне и ПК.

**Этап 8. Безопасность.** Регистрация и вход, токены, роли (admin, user, guest), разграничение прав на инструменты и данные, защита API (лимиты, валидация), шифрование секретов (API-ключи) в БД, журнал аудита, фильтры prompt injection (документы и результаты инструментов не могут менять системные инструкции). *Готово, когда:* набор тестов атак (см. раздел 9) пройден.

**Этап 9. Проверка и самоанализ.** Verification Engine: сверка утверждений с источниками и результатами инструментов, пометки «проверено / предположение / неизвестно», до двух попыток исправления. Планировщик для многоэтапных задач. *Готово, когда:* на наборе вопросов с известными ответами доля выдуманных фактов с источниками снижена относительно базовой модели без проверки (метрика фиксируется).

**Этап 10. Тестирование и оптимизация.** Юнит- и интеграционные тесты, оценочные наборы, нагрузочный тест, профилирование. *Готово, когда:* покрытие ключевых модулей определено и не падает, CI зелёный.

**Этап 11. Развёртывание.** Docker-образы, инструкция по установке, резервное копирование БД и данных, переменные окружения, HTTPS через обратный прокси, документация API. *Готово, когда:* проект поднимается на чистой машине по инструкции за один час.

**Этап 12 (после MVP). Обучение.** Learning Engine: сбор обратной связи, датасеты с версиями, LoRA-дообучение на облачной GPU, оценка новой версии, ручное подтверждение перед включением в production.

## 8. Модели и датасеты

### 8.1. Языковые модели (подключаются через адаптеры)

| Назначение | Кандидаты | Примечание |
|------------|-----------|-----------|
| Диалог и рассуждение (локально, CPU) | Qwen2.5-1.5B/3B-Instruct, Gemma 2 2B | Квантование Q4, медленно на текущем ПК |
| Диалог (облако, API) | Модели провайдеров (ChatAnywhere, Groq, OpenRouter) | Быстро, но зависит от лимитов и политики провайдера |
| Код | Qwen2.5-Coder-7B-Instruct (локально на GPU), бесплатные API | Для MVP достаточно облачных моделей |
| Эмбеддинги | bge-m3 (многоязычная, тяжелее), multilingual-e5-small (легче) | Выбор по скорости на нужном железе |
| Vision | Qwen2-VL-2B (локально), модели через API | Для анализа изображений |
| Речь | Whisper small/medium (этап 10+) | Распознавание речи |

### 8.2. Датасеты для дообучения (этап 12)

Использовать только данные с понятной лицензией. Для каждого датасета записывать источник, лицензию и дату.

- OpenAssistant (OASST2) — инструкции и диалоги, открытая лицензия.
- Aya-датасеты — многоязычные инструкции.
- Собственные данные пользователя — только с согласия и с возможностью удаления.
- Оценочные наборы: собственные вопросы с проверенными ответами по русскому и английскому, задачи на код с тестами, арифметика и логика.

Важно: лицензии датасетов и моделей меняются. Перед использованием проверяйте актуальные условия.

## 9. План тестирования

| Уровень | Что проверяем | Инструменты |
|---------|---------------|-------------|
| Юнит-тесты | Отдельные функции и классы модулей | pytest |
| Интеграционные | Связка модулей: запрос → память → инструмент → ответ | pytest, тестовые провайдеры-заглушки (только в тестах) |
| Контрактные | Адаптеры провайдеров соответствуют интерфейсу | pytest + записанные ответы |
| Качество ответов (eval) | Точность фактов, следование инструкциям, русский язык | Наборы в `tests/eval/`, скрипт оценки |
| Безопасность | Prompt injection, попытки выхода из sandbox, утечки ключей, доступ без прав | Набор атак в `tests/security/` |
| UI | Основные сценарии в браузере, мобильная вёрстка | Playwright |
| Нагрузка | Параллельные диалоги, время ответа, память | locust или k6 |
| Регрессия | Сравнение версий моделей и промптов на одном наборе | Скрипт `scripts/eval_compare.py` |

**Правило:** модуль не считается готовым без тестов. Изменение промпта или модели без прогона eval-набора в production не выкатывается.

## 10. Риски и ограничения

| Риск | Вероятность | Влияние | Меры |
|------|------------|---------|------|
| Собственная модель уступает облачным по качеству | Высокая | Высокое | Архитектура с подключаемыми моделями; дообучение только по измеримой метрике |
| Недостаток ресурсов (CPU, RAM, GPU) | Высокая | Высокое | Облачные API на MVP, квантованные малые модели локально, аренда GPU для обучения |
| Лимиты и политика бесплатных API меняются | Высокая | Среднее | Несколько провайдеров, автоматическое переключение, локальная запасная модель |
| Выдумывание фактов (галлюцинации) | Высокая | Высокое | Verification Engine, пометки уверенности, источники, тесты на фактах |
| Выполнение вредоносного кода | Средняя | Критическое | Sandbox в Docker без сети, лимиты ресурсов, подтверждение пользователя |
| Prompt injection через документы и веб | Высокая | Высокое | Разделение данных и инструкций, фильтры, документы не меняют системные правила |
| Утечка персональных данных | Средняя | Критическое | Минимизация данных, шифрование, право на удаление, согласие на запоминание |
| Нарушение лицензий моделей и датасетов | Средняя | Высокое | Реестр лицензий, проверка перед использованием |
| Раздувание проекта (слишком много функций сразу) | Высокая | Высокое | Приоритет MVP, функции этапа 2+ не начинаются раньше готовности MVP |
| Потеря данных | Низкая | Высокое | Резервное копирование БД и `data/` по расписанию |

**Юридическая оговорка:** при работе с персональными данными учитывать требования законодательства страны пользователей (например, 152-ФЗ в России или GDPR в ЕС). Это не юридическая консультация, при необходимости обращайтесь к специалисту.

## 11. Что будет проверено и сделано в первую очередь

Сразу после утверждения плана:
1. Создать структуру каталогов и `pyproject.toml`.
2. Установить Docker (нужен для sandbox и Compose) — это единственная системная зависимость, которой сейчас нет.
3. Написать ADR-записи для ключевых решений: выбор FastAPI, SQLite → PostgreSQL, sqlite-vec → Qdrant, подход к моделям через адаптеры.
4. Реализовать этап 2 (основа) и этап 3 (ядро с адаптером провайдера).

## 12. Двадцать функций, которые усилят Kali

1. **Автоматический выбор модели** под задачу: дешёвая для простого, сильная для сложного, с учётом лимитов провайдера.
2. **Кэш ответов** для повторяющихся вопросов с проверкой актуальности.
3. **Голосовой ввод и озвучивание** через Whisper и TTS-адаптеры.
4. **Проверка кода тестами**: Kali запускает сгенерированный код на тестах в sandbox прежде, чем показать его.
5. **Режим «объясни как ученику»** с уровнями сложности.
6. **Граф знаний** по загруженным документам: связи между понятиями.
7. **Автоматическая суммаризация длинных диалогов** в долговременную память.
8. **Экспорт проекта** целиком (диалоги, документы, память) в архив с возможностью переноса на другой сервер.
9. **Шаблоны проектов**: заготовки «веб-сайт», «телеграм-бот», «анализ таблицы».
10. **Встроенный калькулятор с символьной алгеброй** (через SymPy).
11. **Работа с таблицами**: построение графиков по CSV/XLSX и вопросы к данным на естественном языке.
12. **Напоминания и задачи** с уведомлениями (через фоновые задачи).
13. **Мультиязычный перевод документов** с сохранением структуры.
14. **Режим «критик»**: модель специально ищет слабые места в ответе или плане.
15. **Сравнение ответов нескольких моделей** по одному запросу с оценкой.
16. **Панель качества**: доля ответов с источниками, частота исправлений, время ответа.
17. **Безопасный обмен** ссылкой на диалог с ограниченным сроком действия.
18. **Персональные инструкции по стилю** (тон, длина, формат) для каждого проекта.
19. **Автоматическая очистка памяти** от устаревших и противоречивых фактов с подтверждением.
20. **Плагины сообщества** через защищённый реестр, с проверкой подписи и разрешений.

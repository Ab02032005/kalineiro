# Kali — архитектура и план (Этап 1)

> Документ первого этапа. Код на этом этапе не пишется. Здесь описано, что будет построено, на чём, в каком порядке и с какими ограничениями.

## 0. Главные выводы (честно)

1. **Собственную языковую модель «как у крупных компаний» на этом компьютере создать нельзя.** Обучение такой модели требует тысяч GPU-часов, датасетов из триллионов токенов и кластера. Ryzen 3 3200U с 10 ГБ памяти и встроенной графикой без CUDA для этого не подходит даже для дообучения крупной модели.
2. **Реалистичный путь:** сначала построить собственную платформу Kali (ядро, память, инструменты, агенты, интерфейс, безопасность). Языковые модели подключаются как взаимозаменяемые модули. Потом, при наличии ресурсов, начинается дообучение (LoRA) небольшой открытой модели на собственных данных, и только затем, возможно, претренинг собственной малой модели.
3. **Архитектура Kali не зависит от конкретного API.** Провайдеры (ChatAnywhere, Groq, OpenRouter, локальные модели через Ollama) подключаются через адаптеры. Это решает и текущую проблему с лимитами.
4. **Всё, что Kali «умеет», должно быть реально работающим.** Если функция требует модели, которой нет, Kali не имитирует её, а сообщает, что нужно подключить модель, и показывает требования к ней.

## 1. Цели MVP и границы

**MVP (минимальная жизнеспособная версия)** — это то, что можно сделать и проверить за 3–4 недели:
- чат с несколькими диалогами, историей и потоковыми ответами;
- подключение нескольких провайдеров моделей через единый интерфейс;
- долговременная память (факты и эпизоды) с поиском и удалением по запросу;
- база знаний: загрузка TXT, MD, PDF, DOCX, CSV, XLSX, поиск по ней (RAG) с указанием источников;
- инструменты: калькулятор, создание файлов, генерация изображений через подключаемый провайдер, интернет-поиск;
- выполнение Python-кода в изолированной среде;
- проверка ответов (QA-шаг) и пометка уверенности: «проверено инструментом», «предположение», «неизвестно»;
- авторизация, разграничение прав, журнал действий, защита от prompt injection в базовом объёме;
- веб-интерфейс с разделами Chat, Memory, Knowledge, Files, Models, Settings.

**Вне MVP** (этапы 2+): собственное обучение модели, полноценные мультиагентные сценарии, аудио и видео, самоулучшение, кластерное развёртывание.

## 2. Архитектура

### 2.1. Модули (12 из технического задания)

| № | Модуль | Назначение | Реализация в MVP |
|---|--------|-----------|------------------|
| 1 | Core AI Engine | Оркестратор: принимает запрос, вызывает модули, собирает ответ | Python, FastAPI, асинхронный конвейер |
| 2 | Language Processing | Токенизация, определение языка, нормализация запроса | Через выбранную модель + лёгкие утилиты |
| 3 | Reasoning Engine | Декомпозиция задач, выбор стратегии | Промпт-шаблоны + структурированный вывод (JSON-схемы) |
| 4 | Memory Engine | Краткосрочная, долговременная, эпизодическая, семантическая, процедурная память | PostgreSQL (SQLite в dev) + векторный индекс |
| 5 | Learning Engine | Сбор обратной связи, датасеты, оценка, версии | Таблицы feedback и datasets, скрипты оценки; обучение — этап 3+ |
| 6 | Knowledge Engine | Индексация документов, поиск, цитирование | Чанкование, эмбеддинги, гибридный поиск (вектор + BM25) |
| 7 | Tool Engine | Подключение инструментов без изменения ядра | Реестр инструментов с JSON-схемами и правами |
| 8 | Planning Engine | Многоэтапные задачи, контроль шагов | Машина состояний: план → шаг → проверка → итог |
| 9 | Verification Engine | Проверка фактов и результатов инструментов | Правило: факт допустим только с источником или результатом инструмента |
| 10 | Multimodal Engine | Изображения, документы, таблицы, аудио | Адаптеры: vision-модель, парсеры документов, Whisper (позже) |
| 11 | Security Engine | Авторизация, права, изоляция кода, фильтры | Роли, токены, sandbox, фильтры входа и выхода |
| 12 | API Engine | Внешний интерфейс для других приложений | REST (FastAPI), OpenAPI-документация |

Каждый модуль имеет интерфейс (Python Protocol), собственные тесты и может быть заменён без переписывания остальных.

### 2.3. Жизненный цикл запроса

1. **Приём и авторизация.** API Engine проверяет токен и права пользователя.
2. **Классификация.** Reasoning определяет тип задачи: диалог, вопрос к знаниям, код, расчёт, файл, изображение, многоэтапная задача.
3. **Контекст.** Memory подбирает релевантные факты и эпизоды, Knowledge — фрагменты документов. Всё, что подставлено, помечается источником.
4. **План.** Для простой задачи план из одного шага. Для сложной Planning создаёт список шагов.
5. **Выполнение.** Модель генерирует ответ или вызывает инструменты через Tool Engine. Результаты инструментов сохраняются как есть.
6. **Проверка.** Verification сверяет утверждения с результатами инструментов и источниками. Неподтверждённое помечается как предположение.
7. **Исправление.** Если проверка нашла ошибку, шаг повторяется с замечанием (не более 2 попыток).
8. **Ответ и журнал.** Ответ стримится пользователю. Действия записываются в audit-журнал, важные факты предлагаются к сохранению в память.

### 2.4. Принципы

- **Никаких выдуманных результатов инструментов.** Если инструмент не вызывался или упал, Kali говорит об этом.
- **Подтверждение критичных действий.** Удаление данных, запуск кода с сетевым доступом, отправка писем — только после явного «да» пользователя.
- **Изменение весов в production запрещено без проверки.** Новая версия модели проходит оценку, резервную копию и подтверждение администратора.
- **Провайдер — это плагин.** Замена провайдера не требует изменения ядра.

## 4. Требования к оборудованию

### 4.1. Текущий компьютер
- Процессор: AMD Ryzen 3 3200U, 2 ядра / 4 потока.
- Оперативная память: 10 ГБ.
- Видео: встроенная Radeon Vega 3, около 2 ГБ общей памяти, без CUDA.
- Диск: около 130 ГБ свободно на C, около 670 ГБ на D.
- Python 3.14 установлен, Docker и Git не установлены.

**Что на нём реалистично:** разработка и тесты MVP, Kali API, RAG по документам, память, веб-интерфейс, инструменты, sandbox (через Docker после установки), запуск квантованной модели 1–3B параметров на CPU (медленно, около нескольких токенов в секунду).

**Что нереально:** обучение и дообучение моделей, запуск моделей 7B+ с нормальной скоростью, эмбеддинги большого объёма.

### 4.2. Для дообучения (этап 3)
- LoRA на модели 7–8B: одна GPU с 24 ГБ памяти (например, RTX 4090 или облачная A10/L4). Облачная аренда порядка 0.5–1.5 $ в час, ориентировочно 20–100 часов на один цикл.
- QLoRA на 7B с 16 ГБ памяти: возможно, но медленнее.

### 4.3. Для претренинга собственной модели (этап 4+)
- Сотни миллиардов токенов текста, кластер из десятков или сотен GPU, недели–месяцы работы, бюджет от сотен тысяч долларов. Для текущей задачи это не рекомендуется. Цель этапа 4 — подготовка данных и методики, а не полный претренинг.

## 5. Оценка сложности

Оценки ориентировочные, для одного разработчика с опытом в Python и веб-разработке, занимающегося проектом 2–4 часа в день.

| Этап | Что делается | Оценка |
|------|-------------|--------|
| 1 | Архитектура, стек, план | 2–3 дня |
| 2 | Структура проекта, конфигурация, логирование | 2–3 дня |
| 3 | Ядро (Core, API, Model Gateway с адаптерами) | 1–1.5 недели |
| 4 | Память (4 вида, поиск, удаление, экспорт) | 1 неделя |
| 5 | Подключение модели, потоковые ответы, промпты | 3–5 дней |
| 6 | Инструменты, Tool Engine, sandbox, агенты (базовые) | 1.5–2 недели |
| 7 | Пользовательский интерфейс (все разделы) | 2 недели |
| 8 | Безопасность (авторизация, права, аудит, защита) | 1 неделя |
| 9 | Тестирование, оптимизация | 1 неделя |
| 10 | Развёртывание (Docker, CI, документация) | 3–5 дней |
| **Итого MVP** | | **≈ 8–10 недель** |
| Этап 3+ | LoRA-дообучение, Learning Engine с оценкой | 3–4 недели |
| Полная версия | Мультиагенты, мультимодальность, Research & Improvement | 6–12 месяцев |

Главные факторы сложности: качество промптов и проверки ответов, безопасность выполнения кода, консистентность памяти и поиска.
